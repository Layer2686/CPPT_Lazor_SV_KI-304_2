## 2. Мета роботи

Перетворити CSV-записи на незмінні об’єкти з перевіркою стану, використати
record і зберегти зовнішню поведінку програми. Підтвердити сумісність тестами
й запуском обох реалізацій. Додатково реалізувати builder без обходу перевірок.

## 4. Клас-сутність

WeatherReading — final-клас із private final-полями date, temperatureHumidity,
pressure і wind. Record зберігає два числові компоненти — temperature та humidity,
тобто модель містить усі п’ять значень CSV без дублювання стану.

Конструктор перевіряє всі поля, геттери надають доступ лише для читання.
Дата зберігається як YYYY-MM-DD без календарного розбору. Температура — скінченна,
може бути від’ємною; вологість 0–100; тиск >0; вітер >=0. Числа NaN та Infinity
відхиляються. Порожня, null або неправильно записана дата відхиляється.

Метод toString повертає текст із двома десятковими знаками через Locale.ROOT:

```text
2026-09-01: -5.50 °C, 70.00 %, 1013.00 гПа, 3.20 м/с
```

Він призначений для представлення об’єкта; сумісний консольний вивід записів
першої лабораторної збережено окремо.

## 5. Фабрика, record та builder

fromCsv приймає рядок date;temperature;humidity;pressure;wind, зберігає порожнє
останнє поле через split(";", -1), прибирає крайні пробіли й виконує parseDouble.
Порядок перевірок вологості, вітру, температури, тиску й дати збережено з LAB_01.
Спільні методи перевірок не дублюють діапазони. Конструктор перевіряє стан
незалежно від фабрики, тому пряме створення об’єкта також безпечне.

TemperatureHumidity — record із перевіреним компактним конструктором.
Він реально зберігається у WeatherReading й використовується WeatherReport
для обчислення мінімуму температури та суми вологості. Методи доступу,
equals, hashCode і toString для record створює Java.

Builder дозволяє задавати п’ять параметрів по черзі, а build викликає конструктор.
Незадані числа позначено NaN, дата — null; неповний об’єкт не створюється.
Сам builder змінний і не призначений для спільного використання потоками.
Готове вимірювання незмінне, не має сеттерів і не зберігає посилання на builder.
Тому інший потік не може змінити його поля; це зменшує ризик гонок під час
читання спільних даних. Подальша зміна builder не впливає на попередній результат.

## 6. Тестування

MainTest містить усі 12 перевірок першої реалізації: показники, межі, помилки
структури й чисел, порожній файл, CLI, UTF-8, файли та незалежність від локалі.
WeatherReadingTest містить 12 нових простих @Test:

- збереження всіх полів конструктором;
- null, порожня й неправильно записана дата;
- вихід за діапазони й недодатний тиск;
- NaN та нескінченності;
- допустимі межі й від’ємна температура;
- fromCsv і пробіли;
- структура CSV, null і хибне число;
- порядок першої помилки та відхилення хибного стану;
- доступ і рівність значень record;
- toString за німецької локалі;
- незалежність результату від подальших змін builder;
- неможливість обійти перевірки через builder.

Локальний verify: LAB_01 — 12 тестів, LAB_02 — 24; failures/errors/skipped — 0.
SpotBugs — 0 дефектів і 0 помилок аналізу в обох модулях.

## 7. Інфраструктура

Спільні Maven Wrapper 3.3.4, Maven 3.9.9 і Java 21 збережено. LAB_02 використовує
ті самі версії JUnit 5.13.4, Surefire 3.5.4, SpotBugs 4.10.4.1 та Shade 3.6.2.
Кореневий POM залишається агрегатором версії 1.0.0; LAB_02 має власну 1.1.0.
Main-Class другого JAR: ua.lpnu.kzp.lab02.Main.

Команди з кореня на Linux/macOS:

```sh
./mvnw -B test
./mvnw -B verify
./mvnw -B package
java "-Dstdout.encoding=UTF-8" "-Dstderr.encoding=UTF-8" -jar LAB_02/target/lab02.jar --input LAB_02/data/input.csv --output LAB_02/out/report.txt
```

На Windows використовується `.\mvnw.cmd` замість `./mvnw`, а для консолі —
UTF-8, як описано в README. CI виконує clean verify на Ubuntu, Windows і macOS,
запускає обидва JAR, читає очікувану версію з POM і порівнює звіти двох програм.
Кожна ОС публікує окремі lab01/lab02 артефакти. Javadoc генерується з -Werror.

Фактичні посилання CI, артефактів і тега будуть додані після їх перевірки.

## 9. Порівняння поведінки

Вхідний файл збережено з LAB_01:

```text
2026-09-01;-5.5;70.0;1013.0;3.2
2026-09-02;2.0;80.0;1008.0;7.5
2026-09-03;10.0;60.0;1010.0;1.8
2026-09-04;4.0;помилка;1012.0;2.0
2026-09-05;6.0;65.0;1011.0;-1.0
```

Обидва JAR дають ідентичний консольний результат і файловий звіт UTF-8.
Звіт порівняно побайтово з результатом першої програми, збереженим до перебудови.
Той самий контроль повторюється в CI на кожній ОС.

```text
Мінімальна температура: -5.50 °C
Максимальна швидкість вітру: 7.50 м/с
Середній рівень вологості: 70.00 %
Кількість коректних записів: 3
Помилки:
Рядок 4: вологість не є числом; вхід: 2026-09-04;4.0;помилка;1012.0;2.0
Рядок 5: вітер має бути скінченним невід’ємним числом; вхід: 2026-09-05;6.0;65.0;1011.0;-1.0
```

Без коректних записів обидві реалізації виводять «Немає даних» і кількість 0.
Помилка рядка залишається в загальному звіті, не змінює статистику й не
перериває обробку наступних рядків.

## 11. Висновки

Метеостанція перебудована на об’єктну модель зі збереженням CSV та звіту.
Інкапсуляція й конструктор не дозволяють створити некоректний стан, record
компактно описує пару значень, builder створює вимірювання через перевірений
конструктор. Обидві лабораторні запускаються окремо. Модель є основою
для спадкування, enum та поліморфізму в лабораторній №3.
