## 2. Мета роботи

Перетворити CSV-записи на незмінні об’єкти з перевіркою стану, використати
record і зберегти зовнішню поведінку програми. Підтвердити сумісність тестами
й запуском обох реалізацій. Додатково реалізувати builder без обходу перевірок.

Досягнуто:

- заміна рядків і паралельних змінних одного вимірювання власним класом;
- приховування стану, перевірка інваріантів у конструкторі та методи читання;
- створення об’єктів із CSV через статичну фабрику;
- використання record для незмінної пари температури й вологості;
- збереження CSV, правил валідації, показників і зовнішнього звіту LAB_01;
- перенесення попередніх тестів і додавання перевірок нових класів;
- працездатні Maven verify, виконувані JAR та CI на трьох ОС.

## 4. Клас-сутність

WeatherReading — final-клас із private final-полями date, temperatureHumidity,
pressure і wind. Record зберігає два числові компоненти — temperature та humidity,
тобто модель містить усі п’ять значень CSV без дублювання стану.

Конструктор перевіряє всі поля, геттери надають доступ лише для читання.
Дата зберігається як YYYY-MM-DD без календарного розбору. Температура — скінченна,
може бути від’ємною; вологість 0–100; тиск >0; вітер >=0. Числа NaN та Infinity
відхиляються. Порожня, null або неправильно записана дата відхиляється.

| Значення | Поле моделі | Інваріант |
| --- | --- | --- |
| Дата | date | Непорожній текст формату YYYY-MM-DD; календарна правильність не перевіряється |
| Температура, °C | temperatureHumidity.temperature | Скінченне число; від’ємні значення дозволені |
| Вологість, % | temperatureHumidity.humidity | Скінченне число від 0 до 100 включно |
| Тиск, гПа | pressure | Додатне скінченне число |
| Вітер, м/с | wind | Скінченне невід’ємне число |

Публічний конструктор приймає дату, температуру, вологість, тиск і вітер.
Геттери getDate, getTemperature, getHumidity, getPressure та getWind
повертають значення; getTemperatureHumidity повертає незмінну пару.
Відкритих сеттерів немає. Стан доступний лише для читання, а відхилення
неправильних аргументів відбувається до успішного завершення конструктора.

Метод toString повертає текст із двома десятковими знаками через Locale.ROOT:

```text
2026-09-01: -5.50 °C, 70.00 %, 1013.00 гПа, 3.20 м/с
```

Він призначений для представлення об’єкта; сумісний консольний вивід записів
першої лабораторної збережено окремо.

## 5. Фабрика, record та builder

fromCsv приймає рядок date;temperature;humidity;pressure;wind, зберігає порожнє
останнє поле через split(";", -1), прибирає крайні пробіли й виконує parseDouble.
Порядок перевірок вологості, вітру, температури, тиску й дати збережено з LAB_01.
Спільні методи перевірок не дублюють діапазони. Конструктор перевіряє стан
незалежно від фабрики, тому пряме створення об’єкта також безпечне.

CSV має кодування UTF-8, не містить заголовка. Десятковий роздільник — крапка.
У кожному рядку повинно бути рівно п’ять полів. Некоректний рядок не
додається до списку вимірювань і не змінює статистику; його фізичний номер
та перша причина відхилення додаються до списку помилок. Наступні рядки
продовжують оброблятися. Спільні перевірки викликаються повторно
конструктором, але самі правила не скопійовані у фабрику й конструктор.

TemperatureHumidity — record із перевіреним компактним конструктором.
Він реально зберігається у WeatherReading й використовується WeatherReport
для обчислення мінімуму температури та суми вологості. Методи доступу,
equals, hashCode і toString для record створює Java.

Builder дозволяє задавати п’ять параметрів по черзі, а build викликає конструктор.
Незадані числа позначено NaN, дата — null; неповний об’єкт не створюється.
Сам builder змінний і не призначений для спільного використання потоками.
Готове вимірювання незмінне, не має сеттерів і не зберігає посилання на builder.
Тому інший потік не може змінити його поля; це зменшує ризик гонок під час
читання спільних даних. Подальша зміна builder не впливає на попередній результат.

Приклад створення через builder:

```java
WeatherReading reading = WeatherReading.builder()
        .date("2026-09-01")
        .temperature(-5.5)
        .humidity(70)
        .pressure(1013)
        .wind(3.2)
        .build();
```

Відсутність змінюваного стану в готовому вимірюванні зменшує потребу
узгоджувати читання його полів між потоками. Це властивість моделі;
паралельної обробки CSV в цій лабораторній не додавалося.

## 6. Тестування

MainTest містить усі 12 перевірок першої реалізації: показники, межі, помилки
структури й чисел, порожній файл, CLI, UTF-8, файли та незалежність від локалі.
WeatherReadingTest містить 12 нових простих @Test:

- збереження всіх полів конструктором;
- null, порожня й неправильно записана дата;
- вихід за діапазони й недодатний тиск;
- NaN та нескінченності;
- допустимі межі й від’ємна температура;
- fromCsv і пробіли;
- структура CSV, null і хибне число;
- порядок першої помилки та відхилення хибного стану;
- доступ і рівність значень record;
- toString за німецької локалі;
- незалежність результату від подальших змін builder;
- неможливість обійти перевірки через builder.

Додано ArgumentParserTest (6 тестів) і WeatherFileServiceTest (3 тести).
Перевірено типові шляхи, обидва порядки ключів, повторні ключі, режими
довідки/версії, хибні аргументи, UTF-8, заміну вмісту й помилки файлів.
Попередні MainTest та WeatherReadingTest залишені без змін.

відповідного модуля.

## 7. Інфраструктура

Спільні Maven Wrapper 3.3.4, Maven 3.9.9 і Java 21 збережено. LAB_02 використовує
ті самі версії JUnit 5.13.4, Surefire 3.5.4, SpotBugs 4.10.4.1 та Shade 3.6.2.

Main-Class другого JAR: ua.lpnu.kzp.lab02.Main.

Команди з кореня на Linux/macOS:

```sh
./mvnw -B -pl LAB_02 -am test
./mvnw -B -pl LAB_02 -am package
./mvnw -B -pl LAB_02 -am verify
java "-Dstdout.encoding=UTF-8" "-Dstderr.encoding=UTF-8" -jar LAB_02/target/lab02.jar --input LAB_02/data/input.csv --output LAB_02/out/report.txt
```

На Windows PowerShell:

```powershell
.\mvnw.cmd -B -pl LAB_02 -am verify
[Console]::OutputEncoding = [System.Text.UTF8Encoding]::new($false)
java "-Dstdout.encoding=UTF-8" "-Dstderr.encoding=UTF-8" -jar LAB_02/target/lab02.jar --input LAB_02/data/input.csv --output LAB_02/out/report.txt
```

Фаза verify включає test і package, тому для повної перевірки достатньо
однієї команди verify. Команда без `-pl LAB_02 -am` збирає обидва модулі.

## 9. Порівняння поведінки

Вхідний файл [data/input.csv](data/input.csv) збережено з LAB_01:

```text
2026-09-01;-5.5;70.0;1013.0;3.2
2026-09-02;2.0;80.0;1008.0;7.5
2026-09-03;10.0;60.0;1010.0;1.8
2026-09-04;4.0;помилка;1012.0;2.0
2026-09-05;6.0;65.0;1011.0;-1.0
```

Обидва JAR дають ідентичний консольний результат і файловий звіт UTF-8.
Звіт порівняно побайтово з результатом першої програми, збереженим до перебудови.
Той самий контроль повторюється в CI на кожній ОС.

Запуск із кореня репозиторію після збірки:

```sh
java "-Dstdout.encoding=UTF-8" "-Dstderr.encoding=UTF-8" -jar LAB_02/target/lab02.jar --input LAB_02/data/input.csv --output LAB_02/out/report.txt
```

Спочатку консоль показує три коректні записи:

```text
Рядок 1: дата 2026-09-01, температура -5.5 °C, вологість 70.0 %, тиск 1013.0 гПа, вітер 3.2 м/с
Рядок 2: дата 2026-09-02, температура 2.0 °C, вологість 80.0 %, тиск 1008.0 гПа, вітер 7.5 м/с
Рядок 3: дата 2026-09-03, температура 10.0 °C, вологість 60.0 %, тиск 1010.0 гПа, вітер 1.8 м/с
```

Далі виводиться підсумок. Саме підсумок із помилками також записується
у LAB_02/out/report.txt; докладні рядки коректних вимірювань залишаються
лише в консолі. Батьківський каталог файла створюється автоматично.

```text
Мінімальна температура: -5.50 °C
Максимальна швидкість вітру: 7.50 м/с
Середній рівень вологості: 70.00 %
Кількість коректних записів: 3
Помилки:
Рядок 4: вологість не є числом; вхід: 2026-09-04;4.0;помилка;1012.0;2.0
Рядок 5: вітер має бути скінченним невід’ємним числом; вхід: 2026-09-05;6.0;65.0;1011.0;-1.0
```

Без коректних записів обидві реалізації виводять «Немає даних» і кількість 0.
Помилка рядка залишається в загальному звіті, не змінює статистику й не
перериває обробку наступних рядків.

Ручна перевірка показників: min(-5.5, 2, 10) = -5.5;
(70 + 80 + 60) / 3 = 70; max(3.2, 7.5, 1.8) = 7.5;
кількість коректних записів — 3. Отже, перебудова моделі зберегла
результати варіанта 18.

## 11. Академічна доброчесність

**Інструмент:** ChatGPT / Codex.

**Характер допомоги:** під час роботи використовувалися консультації ШІ
щодо планування, структури програми, Java-коду, збірки та тестування.
ШІ виконував роль консультанта й ментора з пояснення синтаксису,
взаємодії класів, конструкторів, record та роботи з файлами.
Цей звіт також оформлено за допомогою ШІ.

У роботі збережено й використано Maven Wrapper та засоби перевірки
першої лабораторної. Рішення щодо окремого модуля LAB_02, малого Main,
парсера параметрів і контролера узгоджувалися під час консультацій
з урахуванням уточнення викладача.

**Участь студента:** визначення варіанта та вимог, розробка плану й структури,
реалізація предметної області. 

Технічні результати підтверджуються тестами, запусками JAR і наведеними
посиланнями на CI. 

## 12. Висновки

Метеостанція перебудована на об’єктну модель зі збереженням CSV та звіту.
Інкапсуляція й конструктор не дозволяють створити некоректний стан, record
компактно описує пару значень, builder створює вимірювання через перевірений
конструктор. Обидві лабораторні запускаються окремо. Модель є основою
для спадкування, enum та поліморфізму в лабораторній №3.

Виконані вимоги трьох рівнів: об’єктна модель зі збереженням поведінки;
старі й нові JUnit-тести, статичний аналіз та виконуваний JAR;
CI на трьох ОС, артефакти й фінальний тег v1.1.1.
Додаткове завдання — незмінна сутність із builder — реалізовано
через той самий перевірений конструктор.
