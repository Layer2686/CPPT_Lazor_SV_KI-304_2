## Мета
Мета роботи — пройти повний шлях від створення репозиторію й налаштування інфраструктури до версії простої консольної програми, яку можна відтворено зібрати й запустити на Windows, macOS та Ubuntu.

Після виконання роботи Ви зможете:
* створювати Java-проєкт із системою збирання Maven;
* підключати зовнішні бібліотеки через pom.xml, не копіюючи їх у репозиторій;
* організовувати код, тести, документацію та дані в репозиторії GitHub;
* читати текстові записи, перевіряти їх і виконувати базові числові обчислення;
* форматовано виводити результат у консоль і текстовий файл;
* запускати збірку, тести й статичний аналізатор через Maven;
* налаштовувати GitHub Actions і публікувати зібрану програму як артефакт;
* працювати з GitHub Issues і Pull Request.

## ТЕОРЕТИЧНІ ВІДОМОСТІ

### 1. Інфраструктура проєкту: від репозиторію до CI/CD
Розробка програмного проєкту починається не з написання предметного коду. Спочатку налаштовують інфраструктуру, яка дає змогу зберігати зміни, однаково будувати проєкт, запускати перевірки та доставляти результат. Тоді програма стає відтворюваною: інша людина або автоматичний сервер може отримати той самий код і виконати ті самі кроки.

Розробка проєкту в репозиторії починається з базової структури. Далі проєкт описується в Maven, після чого поступово додаються налаштування для відтворюваного запуску, тестування, перевірки якості та пакування. На наступному етапі ті самі перевірки переносяться до GitHub Actions, а зміни пов'язуються з GitHub Issues i Pull Request.

#### 1.1. Створення репозиторію та базових правил
Щоб створити публічний репозиторій, увійдіть до GitHub і виберіть New repository. Укажіть назву, що містить номер роботи та Ваше прізвище, наприклад `kzp-lab01-petrenko`, виберіть видимість Public і натисніть Create repository. Якщо Ви створюєте базові файли локально, не додавайте їх автоматично на GitHub. Скопіюйте URL зі сторінки репозиторію та клонуйте його:

```text
git clone https://github.com/<ваш-логін>/kzp-lab01-petrenko.git
```

Після клонування додайте файли у VS Code та виконайте перший commit i push. На першому кроці достатньо підготувати структуру без предметної логіки:

```text
project/
├── README.md
├── REPORT.md
├── .gitignore
├── .gitattributes
├── .editorconfig
├── data/
├── src/main/java/
└── src/test/java/
```

`README.md` пояснює призначення проєкту й команди запуску, `REPORT.md` стане звітом, а службові файли фіксують правила, спільні для всіх ОС. Наприклад, `.gitignore` не дає додати до Git результати локальної збірки та налаштування IDE:

```gitignore
target/
.idea/
*.iml
.vscode/
```

Ці правила не приховують вихідний код: вони прибирають лише файли, які Maven або середовище розробки можуть відтворити. Повніші приклади `.gitignore`, `.gitattributes`, `.editorconfig` i `README.md` наведено в Додатку А.

#### 1.2. Опис проєкту в pom.xml
Maven не вгадує властивості проєкту з назв каталогів. Їх явно задають у `pom.xml`. Мінімальний фрагмент містить координати проєкту, версію Java та кодування:

```xml
<project>
    <modelVersion>4.0.0</modelVersion>
    <groupId>ua.lpnu.kzp</groupId>
    <artifactId>lab01</artifactId>
    <version>1.0.0</version>
    <properties>
        <maven.compiler.release>21</maven.compiler.release>
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
        <project.reporting.outputEncoding>UTF-8</project.reporting.outputEncoding>
    </properties>
</project>
```

`groupId`, `artifactId` i `version` утворюють координати артефакта — його однозначний ідентифікатор y Maven:

| Елемент | Призначення | Значення у прикладі |
| :--- | :--- | :--- |
| **groupId** | група або організація, якій належить проєкт; часто використовується обернений домен | ua.lpnu.kzp |
| **artifactId** | назва конкретного проєкту або бібліотеки | lab01 |
| **version** | версія артефакта | 1.0.0 |

У скороченому записі ці координати мають вигляд `ua.lpnu.kzp:lab01:1.0.0`. За ними Maven розрізняє проєкти та версії під час збирання і роботи із залежностями. Властивість release обмежує мову та АРІ Java версією 21, а явне UTF-8 не залежить від локальних налаштувань. Це фрагмент для пояснення, а не готовий файл: повний приклад із залежністю JUnit, аналізатором і пакуванням наведено в Додатку А.

#### 1.3. Відтворювана збірка через Maven Wrapper
Звичайна команда `mvn` використовує Maven, установлений у системі. Щоб не вимагати однакової локальної установки, у репозиторій додають Maven Wrapper — скрипти `mvnw` i `mvnw.cmd` разом із каталогом `.mvn/wrapper/`. Wrapper генерується одноразово командою `mvn wrapper:wrapper` (для цього потрібна глобальна установка Maven) і далі зберігається в репозиторії. Після цього глобальний Maven більше не потрібен:

```text
mvn wrapper:wrapper
```

Після цього на Unix-подібних системах використовуйте `./mvnw`, a y Windows — `mvnw.cmd`:

```text
./mvnw test
mvnw.cmd test
```

Wrapper завантажує визначену версію Maven під час першого запуску. Він не замінює JDK: Java 21 все одно має бути встановлена або на локальному комп'ютері, або на runner CI.

#### 1.4. Тести як частина збірки
Тести зберігають у `src/test/java/`, а не поруч із кодом програми. JUnit підключають як тестову залежність у `pom.xml`, тому бібліотеку не копіюють до репозиторію:

```xml
<dependency>
    <groupId>org.junit.jupiter</groupId>
    <artifactId>junit-jupiter</artifactId>
    <version>5.12.2</version>
    <scope>test</scope>
</dependency>
```

Позначка `<scope>test</scope>` означає, що залежність потрібна для компіляції та запуску тестів, але не є частиною програми під час звичайного запуску. Команда test має пройти до того, як Ви переходите до статичного аналізу та пакування.

#### 1.5. Перевірка якості та створення JAR
Після тестів Maven може виконати статичний аналізатор. SpotBugs аналізує скомпільований байт-код (не вихідний текст), тому він запускається після фази компіляції. Його прив'язують до фази verify, щоб команда перевіряла не лише компіляцію:

```xml
<plugin>
    <groupId>com.github.spotbugs</groupId>
    <artifactId>spotbugs-maven-plugin</artifactId>
    <version>4.9.7.0</version>
    <executions>
        <execution>
            <phase>verify</phase>
            <goals><goal>check</goal></goals>
        </execution>
    </executions>
</plugin>
```

Плагін пакування збирає JAR, який можна передати іншому користувачеві. Для виконуваного JAR у конфігурації потрібно вказати клас із методом main:

```xml
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-shade-plugin</artifactId>
    <version>3.6.0</version>
    <executions>
        <execution>
            <phase>package</phase>
            <goals><goal>shade</goal></goals>
            <configuration>
                <transformers>
                    <transformer implementation="org.apache.maven.plugins.shade.resource.ManifestResourceTransformer">
                        <mainClass>ua.lpnu.kzp.Main</mainClass>
                    </transformer>
                </transformers>
            </configuration>
        </execution>
    </executions>
</plugin>
```

У своєму проєкті замініть `ua.lpnu.kzp.Main` на фактичний повний клас із main. Послідовність `test` -> `verify` -> `package` означає: спочатку перевірити поведінку, потім якість, а вже після цього сформувати результат для передачі.

#### 1.6. Автоматична перевірка в GitHub Actions
Локальна зелена збірка ще не доводить кросплатформність. GitHub Actions запускає той самий Wrapper на Windows, macOS та Ubuntu. Автоматичний запуск збірки й перевірок для кожної зміни називають continuous integration (CI). Матриця створює окремий запуск для кожної ОС:

```yaml
name: CI
on:
  push:
  pull_request:
jobs:
  verify:
    strategy:
      matrix:
        os: [ubuntu-latest, windows-latest, macos-latest]
    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '21'
          cache: maven
      - name: Verify on Unix
        if: runner.os != 'Windows'
        run: ./mvnw -B verify
      - name: Verify on Windows
        if: runner.os == 'Windows'
        run: .\mvnw.cmd -B verify
```

`checkout` отримує код, `setup-java` встановлює JDK і кешує залежності, a `verify` повторює локальну перевірку на runner. Після успішної перевірки JAR можна опублікувати як артефакт:

```yaml
      - uses: actions/upload-artifact@v4
        with:
          name: jar-${{ matrix.os }}-${{ github.run_number }}
          path: target/*.jar
          if-no-files-found: error
```

Артефакт є результатом continuous delivery у межах цієї роботи: його можна завантажити зі сторінки workflow. Повний фрагмент workflow, зокрема умови для Windows i Unix, наведено в Додатку А.

#### 1.7. Планування через GitHub Issues i Pull Request
GitHub Issues документують окремі завдання та дефекти, а Pull Request об'єднує зміни та запускає СІ. Типовий потік має такий вигляд:

```text
GitHub Issue -> гілка -> коміти -> Pull Request -> CI -> виправлення -> merge
```

На початку створіть у GitHub окремі Issues для інфраструктури, предметної програми, документації та дефектів. У Pull Request додайте короткий опис, приклад запуску, стан СІ та зв'язок із завданням через `Closes #N`. Тут N — номер конкретного GitHub Issue. Наприклад, для Issue з номером 12 в описі Pull Request напишіть `Closes #12`. Після злиття Pull Request у гілку за замовчуванням GitHub автоматично закриває пов'язане Issue.

Форми GitHub Issues і чек-лист Pull Request подано в Додатку А.
Після налаштування репозиторію поверніться до команди verify: у наступних розділах Ви додасте до цього проєкту клас Java, обробку даних, звіт і тести. Приклади пов'язаних файлів зібрано в Додатку А.

### 2. Фази життєвого циклу Maven
Структура `pom.xml`, координати артефакта, Мaven Wrapper, залежності, аналізатор і пакування пояснено вище (підрозділи 1.2-1.5). Повний приклад `pom.xml` наведено в Додатку А.
Maven виконує фази (англ. phases) у фіксованому порядку. Виклик пізнішої фази автоматично виконує всі попередні:

| Команда | Що виконується |
| :--- | :--- |
| `mvnw.cmd compile` або `./mvnw compile` | лише компіляція |
| `mvnw.cmd test` або `./mvnw test` | компіляція + запуск тестів |
| `mvnw.cmd verify` aбo `./mvnw verify` | компіляція + тести + перевірки (SpotBugs) |
| `mvnw.cmd package` або `./mvnw package` | компіляція + тести + перевірки + JAR y `target/` |
| `mvnw.cmd clean` або `./mvnw clean` | очищення результатів попередньої збірки |

Окремий виклик `clean verify` спочатку видаляє `target/`, а потім збирає проєкт і перевіряє його від початку. Це корисно для СІ та перед здачею.

### 3. Будова простої Јаѵа-програми
Мінімальна Java-програма містить клас і метод `main`, із якого починається виконання:

```java
/** Мінімальна консольна програма. */
public final class Main {
    /* Забороняє створення екземплярів службового класу. */
    private Main() {
    }

    /**
     * Точка входу до програми.
     *
     * @param args аргументи командного рядка
     */
    public static void main(String[] args) {
        System.out.printf("Програму запущено%n");
    }
}
```

Назва public-класу має збігатися з назвою файла. Метод `main` приймає масив рядків `String[] args`; аргументи командного рядка дають змогу передати програмі шляхи до входу та виходу, не змінюючи код. Розбір аргументів реалізується простим порівнянням:

```java
if (args.length > 0 && "--help".equals(args[0])) {
    System.out.printf("Використання: java -jar lab01.jar [--help] [--input <файл>] [--output <файл>]%n");
    return;
}
```

У цій роботі використовуються примітивні типи `int`, `long`, `double`, `boolean`, `char` Ta посилальний тип `String`. Тип змінної визначає допустимі значення й операції над ними.

| Тип | Приклад | Використання в роботі |
| :--- | :--- | :--- |
| `int` | 12 | кількість, номер, тривалість у цілих одиницях |
| `long` | 12 000L | велика кількість або сума в найменших одиницях |
| `double` | 12.5 | вимірювання, ціна, рейтинг, середнє |
| `boolean` | true | ознака «так/ні» |
| `String` | "біг" | назва, категорія, дата y форматі YYYY-MM-DD |

### 4. Читання та розбір записів
Вхідний файл `data/input.csv` кодують у UTF-8. Для простоти в роботі використовується роздільник `;`, а не кома: десяткові числа записують із крапкою, наприклад `12.5`, незалежно від локалі операційної системи.

Наприклад, для предметної області «музейні екскурсії» (не збігається з жодним варіантом) файл може мати такий вигляд:
```text
2026-09-01; Aрхеологія; 24; 60;150.00
2026-09-03; Мистецтво; 18;45;120.00
2026-09-05; Космос; 30; 75;180.00
```

Метод `String.split` розділяє рядок на поля:
```java
String[] fields = line.split(";", -1);
// Порожнє останнє поле теж зберігаємо, тому передано другий аргумент -1.
if (fields.length != 5) {
    System.out.printf("Пропущено рядок із неправильною кількістю полів%n");
}
// Перетворення може кинути NumberFormatException для пошкодженого числового поля.
int visitors = Integer.parseInt(fields[2]);
double ticketPrice = Double.parseDouble(fields[4]);
```

`Integer.parseInt` i `Double.parseDouble` можуть повідомити про неправильний запис винятком `NumberFormatException`. У програмі його потрібно перехопити на рівні обробки одного рядка, повідомити про номер рядка й продовжити роботу з іншими коректними записами.

Обов'язково перевіряють:
* порожній рядок;
* кількість полів;
* порожнє обов'язкове текстове поле;
* від'ємне число там, де воно не має сенсу;
* нечислове значення в числовому полі;
* відсутність хоча б одного коректного запису.

**Пастка.** Перехопити виняток і мовчки продовжити роботу не означає обробити помилку. У звіті або окремому повідомленні потрібно вказати номер рядка та причину пропуску.

### 5. Арифметичні обчислення
Для кожного варіанта потрібно обчислити чотири показники, зазначені в таблиці варіантів: кількість коректних записів, суму або середнє одного числового поля, мінімум або максимум іншого поля та ще один предметний показник.

Середнє обчислюють у `double`, інакше цілочислове ділення відкине дробову частину:
```java
import java.util.Locale;

int total = 7;
int count = 2;
// Явне приведення до double не дає цілочисловому діленню відкинути дробову частину.
double average = (double) total / count;
System.out.printf(Locale.ROOT, "Середнє: %.2f%n", average);
```

Для чисел із рухомою крапкою не варто перевіряти рівність через `==`. У тесті використовуйте допустиму похибку:
```java
assertEquals(3.5, actualAverage, 0.0001);
```

Порядок обробки має бути однаковим для всіх рядків: прочитати -> перетворити -> перевірити -> включити в обчислення. Невалідний рядок не повинен змінювати показники.

### 6. Форматований вивід
Для звіту використовуйте `printf` a6o `formatted`, а не конкатенацію рядків через `+`. Під час форматування дробових чисел задавайте `Locale.ROOT` — нейтральну локаль, яка використовує крапку як десятковий роздільник незалежно від налаштувань ОС:

```java
import java.util.Locale;
// %n використовує роздільник рядка поточної операційної системи.
System.out.printf(Locale.ROOT, "%nВсього записів: %d%n", count);
System.out.printf(Locale.ROOT, "Середнє значення: %.2f%n", average);
// String.format i Locale.ROOT гарантує крапку як десятковий роздільник.
String line = String.format(Locale.ROOT, "Всього: %d; середнє: %.2f%n", count, average);
```

Специфікатор `%n` вставляє роздільник рядка, прийнятний для поточної операційної системи. Для однакового вигляду таблиці застосовуйте ширину полів:
```java
import java.util.Locale;
System.out.printf(Locale.ROOT, "%-20s %10s%n", "Показник", "Значення");
System.out.printf(Locale.ROOT, "%-20s %10d%n", "Кількість", count);
System.out.printf(Locale.ROOT, "%-20s %10.2f%n", "Середнє", average);
```

Звіт виводять і в консоль, і у файл, але логіку обчислення не дублюють. Один метод має повернути або сформувати дані звіту, а два різні приймачі можуть їх вивести.

### 7. Робота з файлами та кросплатформність
Шляхи будують через `Path`, а не через конкатенацію рядків із `\\` або `/`:
```java
// Path сам обирає правильний роздільник для Windows, macOS та Ubuntu.
Path input = Path.of("data", "input.csv");
Path output = Path.of("out", "report.txt");
```

Кодування задають явно:
```java
// Кодування задаємо явно, щоб український текст однаково читався на всіх ОС.
List<String> lines = Files.readAllLines(input, StandardCharsets.UTF_8);
// Каталог out може ще не існувати, тому створюємо його перед записом.
Files.createDirectories(output.getParent());
Files.writeString(output, report, StandardCharsets.UTF_8);
```

Не можна припускати, що:
* робоча директорія завжди збігається з директорією проєкту;
* роздільник шляху всюди однаковий;
* стандартне кодування системи — UTF-8;
* порядок файлів у каталозі визначений;
* десятковий роздільник — крапка або кома на всіх комп'ютерах.

У СІ програма перевірятиметься на Windows, macOS та Ubuntu. Саме СІ виявить помилки, які неможливо побачити на одному комп'ютері.

### 8. Тести, статичний аналіз і артефакти
Рівень 1 не вимагає повної інфраструктури, але функціональність і документація мають бути. Для рівня 2 додають Maven, залежності, статичний аналізатор, пакування та GitHub Issues. Для рівня 3 додають тести в СІ на трьох ОС, артефакти та версіювання збірки.

Тестувати потрібно не лише «щасливий шлях» (англ. happy path), тобто звичайний коректний сценарій, коли всі вхідні дані правильні, а й:
* коректний рядок;
* порожній рядок;
* неправильну кількість полів;
* нечислове поле;
* від'ємне значення;
* файл без коректних записів;
* середнє для кількох записів;
* роботу з українськими символами.

Статичний аналізатор запускається під час `verify`. Попередження не слід вимикати без пояснення: якщо правило справді непридатне для конкретного місця, це фіксують у Pull Request.

### 9. GitHub Issues i Pull Request
До початку реалізації створіть у GitHub окремі Issues:

| GitHub Issue | Мітка | Результат |
| :--- | :--- | :--- |
| Налаштувати Maven-проєкт | infra | Wrapper, pom.xml, структура каталогів |

## ДЕМОНСТРАЦІЙНА ПРОГРАМА
Нижче наведено короткий завершений приклад для предметної області «музейні екскурсії». У цій програмі рядок містить текстові та числові поля, а програма перевіряє записи й обчислює показники. Приклад демонструє порядок «прочитати -> перевірити -> обчислити -> вивести».

```java
import java.util.ArrayList;
import java.util.List;
import java.util.Locale;

/** Скорочений приклад обробки записів про музейні екскурсії. */
public final class Lab01Demo {
    /* Забороняє створення екземплярів демонстраційного класу. */
    private Lab01Demo() {
    }

    /**
     * Обробляє кілька заздалегідь заданих рядків.
     *
     * @param args аргументи командного рядка
     */
    public static void main(String[] args) {
        // Останній рядок навмисно містить помилку в числовому полі.
        String[] lines = {
            "2026-09-01; Aрхеологія; 24;60;150.00",
            "2026-09-03; Мистецтво; 18; 45;120.00",
            "2026-09-05; Космос; 30; 75;180.00",
            "2026-09-06; Природа; помилка; 50; 100.00"
        };
        
        List<String> errors = new ArrayList<>(); // Помилки не зупиняють обробку інших рядків.
        int validCount = 0;
        int totalVisitors = 0;
        int totalDuration = 0;
        double maxTicketPrice = Double.NEGATIVE_INFINITY;
        
        for (int index = 0; index < lines.length; index++) {
            // Спочатку перевіряємо структуру рядка, а вже потім перетворюємо його поля.
            String[] fields = lines[index].split(";", -1);
            if (fields.length != 5) {
                errors.add("Рядок %d: очікується 5 полів".formatted(index + 1));
                continue;
            }
            if (fields[0].isBlank() || fields[1].isBlank()) {
                errors.add("Рядок %d: порожня дата або назва експозиції".formatted(index + 1));
                continue;
            }
            try {
                // Числові перетворення виконуються в try, бо вхідні дані можуть бути хибними.
                int visitors = Integer.parseInt(fields[2]);
                int duration = Integer.parseInt(fields[3]);
                double ticketPrice = Double.parseDouble(fields[4]);
                if (visitors < 0 || duration < 0 || ticketPrice < 0) {
                    errors.add("Рядок %d: від'ємне числове значення".formatted(index + 1));
                    continue;
                }
                // До статистики потрапляють лише записи, які пройшли всі перевірки.
                validCount++;
                totalVisitors += visitors;
                totalDuration += duration;
                maxTicketPrice = Math.max(maxTicketPrice, ticketPrice);
            } catch (NumberFormatException exception) {
                errors.add("Рядок %d: числове поле має помилковий формат".formatted(index + 1));
            }
        }
        
        // Окремо обробляємо порожній набір, щоб не ділити на нуль.
        double averageDuration = validCount == 0 ? 0.0 : (double) totalDuration / validCount;
        
        // Один набір обчислених значень виводимо в консоль; у програмі його також записують у файл.
        System.out.printf(Locale.ROOT, "Коректних записів: %d%n", validCount);
        System.out.printf(Locale.ROOT, "Усього відвідувачів: %d%n", totalVisitors);
        System.out.printf(Locale.ROOT, "Середня тривалість: %.2f хв%n", averageDuration);
        System.out.printf(Locale.ROOT, "Найвища ціна квитка: %.2f грн%n", maxTicketPrice);
        System.out.printf(Locale.ROOT, "Помилок: %d%n", errors.size());
        errors.forEach(System.out::println);
    }
}
```

Очікуваний результат для цього набору даних:
```text
Коректних записів: 3
Усього відвідувачів: 72
Середня тривалість: 60.00 хв
Найвища ціна квитка: 180.00 грн
Помилок: 1
Рядок 4: числове поле має помилковий формат
```

Приклад не містить Maven, файлового вводу та тестів: їх Ви додаєте під час виконання роботи. Він показує лише алгоритмічне ядро, яке має залишитися зрозумілим після підключення інфраструктури. У власній роботі поля й показники замінюються відповідно до обраного варіанта.

# Консольний звіт

## Призначення
Програма читає записи з data/input.csv, перевіряє їх, обчислює показники та формує звіт у консоль і файл.

**data/input.csv**
CSV-файл не містить коментарів: кожен непорожній рядок є даними. Приклад для предметної області «музейні екскурсії»:
```text
2026-09-01; Aрхеологія; 24;60;150.00
2026-09-03; Мистецтво; 18;45;120.00
2026-09-05; Космос; 30; 75;180.00
2026-09-06; Природа; помилка; 50; 100.00
```
Три перші рядки коректні, четвертий перевіряє обробку помилки. Коментарі до формату зберігають у `README.md`, а не додають до CSV.

**src/main/java/ua/lpnu/kzp/FileReport.java**
```java
package ua.lpnu.kzp;

import java.io.IOException;
import java.nio.charset.StandardCharsets;
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.List;

/** Ізолює кросплатформне читання та запис текстових файлів. */
public final class FileReport {
    /* Забороняє створення екземплярів службового класу. */
    private FileReport() {
    }

    /**
     * Читає рядки у фіксованому кодуванні UTF-8.
     *
     * @param input шлях до вхідного файла
     * @return рядки файла
     * @throws IOException якщо файл неможливо прочитати
     */
    public static List<String> readLines(Path input) throws IOException {
        // Явне кодування не залежить від налаштувань операційної системи.
        return Files.readAllLines(input, StandardCharsets.UTF_8);
    }

    /**
     * Створює каталог призначення і записує звіт.
     *
     * @param output шлях до файла звіту
     * @param report готовий текст звіту
     * @throws IOException якщо каталог або файл неможливо створити
     */
    public static void writeReport(Path output, String report) throws IOException {
        // Після клонування репозиторію каталог out може ще не існувати.
        Path parent = output.getParent();
        if (parent != null) {
            Files.createDirectories(parent);
            Files.writeString(output, report, StandardCharsets.UTF_8);
        }
    }
}
```
Клас не розв'язує завдання варіанта: він лише ізолює кросплатформну роботу з файлами.

**Основний фрагмент .github/workflows/ci.yml**
```yaml
# Один workflow перевіряє однаковий commit на трьох операційних системах.
name: CI
on:
  push:
  pull_request:
permissions:
  contents: read
jobs:
  verify:
    strategy:
      fail-fast: false
      matrix:
        os: [ubuntu-latest, windows-latest, macos-latest]
    runs-on: ${{ matrix.os }}
    steps:
      # Отримуємо код commit або Pull Request.
      - name: Checkout
        uses: actions/checkout@v4
      # Встановлюємо однаковий JDK 21 і кешуємо залежності Maven.
      - name: Set up Java
        uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '21'
          cache: maven
      # Номер запуску можна використати у version і назві артефакта.
      - name: Show CI build number
        run: echo "CI build ${{ github.run_number }}"
      # На macOS та Ubuntu Wrapper запускають як Unix-скрипт.
      - name: Verify on Unix
        if: runner.os != 'Windows'
        run: ./mvnw -B verify
      # На Windows використовується окремий cmd-скрипт Wrapper.
      - name: Verify on Windows
        if: runner.os == 'Windows'
        run: .\mvnw.cmd -B verify
      # Кожна ОС отримує власний артефакт, щоб результати не перезаписувалися.
      - name: Upload JAR
        if: success()
        uses: actions/upload-artifact@v4
        with:
          name: jar-${{ matrix.os }}-${{ github.run_number }}
          path: target/*.jar
          if-no-files-found: error
```
Це лише орієнтовний фрагмент. Ви самостійно додаєте або змінюєте кроки для тестів, SpotBugs, пакування, версії програми та публікації JAR на всіх трьох ОС.

Файли `feature.yml` i `bug.yml` є формами GitHub Issues, а не файлами Java-програми. Форма `feature.yml` допомагає описати нову функціональну вимогу та критерії її готовності. Форма `bug.yml` потрібна для фіксації дефекту: вона вимагає зазначити кроки відтворення, очікуваний і фактичний результати. Такі форми роблять Issues однаковими за структурою, тому завдання легше планувати, перевіряти й пов'язувати з Pull Request.

**.github/ISSUE_TEMPLATE/feature.yml**
```yaml
# Форма GitHub Issue перетворює вимогу на завдання з перевірюваним критерієм готовності.
name: Feature
description: Запланувати функціональну зміну
title: "[feature] "
labels: ["feature"]
body:
  - type: textarea
    id: description
    attributes:
      label: Опис
      description: Що має з'явитися у програмі?
    validations:
      required: true
  - type: textarea
    id: acceptance
    attributes:
      label: Критерії готовності
      description: Як перевірити, що завдання виконано?
    validations:
      required: true
```

```yaml

body:
  - type: textarea

      label: Кроки відтворення
    validations:
      required: true
  - type: textarea
    id: expected
    attributes:
      label: Очікуваний результат
    validations:
      required: true
  - type: textarea
    id: actual

      label: Фактичний результат
    validations:
      required: true
```
