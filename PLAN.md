## Як працюємо разом

Студент пише предметний Java-код невеликими кроками й пояснює свої рішення.
Асистент пояснює алгоритми, переглядає написаний код, допомагає знаходити
помилки та оформлює репозиторій, документацію й інфраструктуру.
Перед кожним новим фрагментом визначаємо очікувану поведінку та перевірку.
Зберігаємо запити до ШІ, прийняті рекомендації й виправлення для звіту.

Наступним дорученням студент погодив створення GitHub Issues і ролей ШІ.
Предметну реалізацію та налаштування збірки виконуємо окремими етапами.

## 2. Збірка та CI/CD — рівні 2 і 3

1. Зафіксувати JDK 21 через `maven.compiler.release` та явне UTF-8.
2. Згенерувати офіційний Maven Wrapper; зафіксувати версію Maven,
   зберегти скрипти та конфігурацію; надати `mvnw` право виконання в Git.
   На цьому комп'ютері глобального Maven немає, тому для генерації
   використати тимчасовий Maven у `/tmp` або Maven із IDE.
3. Додати JUnit **5** у тестовій області та Surefire. Версії залежностей
   і плагінів перевірити в Maven Central та явно зафіксувати.
4. Прив'язати `spotbugs:check` до `verify`; виправляти попередження або
   документувати конкретне обґрунтоване виключення.
5. Через Maven Shade створити виконуваний JAR із runtime-залежностями
   й `Main-Class`. JUnit як тестова залежність до нього не входить.
6. Зафіксувати версію продукту `1.0.0`; підготувати ресурс із версією
   з Maven і номером CI-збірки. Локальну збірку явно позначати `local`.
7. Додати Actions на `push` і `pull_request` з матрицею
   `ubuntu-latest`, `windows-latest`, `macos-latest`, Temurin 21,
   кешем Maven й `fail-fast: false`.
8. На кожній ОС виконати `clean verify` через відповідний Wrapper.
   Після успіху запустити зібраний JAR: `--help`, `--version`, приклад
   із `--input` та `--output`; перевірити очікувані показники й файл.
9. Публікувати саме виконуваний JAR кожної ОС через `upload-artifact`,
   з назвою, що містить ОС і `github.run_number`.
10. Передавати `github.run_number` у ресурс програми під час збірки,
    щоб `--version` показував версію **і** номер CI-збірки.

Основні майбутні команди з кореня репозиторію:

```text
# Linux / macOS
./mvnw -B clean verify

# Windows PowerShell
.\mvnw.cmd -B clean verify

# Запуск із кореня; назва JAR задана в LAB_01/pom.xml
java -jar LAB_01/target/lab01.jar --help
java -jar LAB_01/target/lab01.jar --version
java -jar LAB_01/target/lab01.jar --input LAB_01/data/input.csv --output out/report.txt
```

У методичці є неточність про порядок фаз Maven. Фактичний порядок —
`compile → test → package → verify`; отже, `clean verify` виконує пакування
перед аналізом у `verify`, а `package` саме по собі не запускає аналіз,
прив'язаний до `verify`. Це підтверджує
[офіційний опис Maven lifecycle](https://maven.apache.org/guides/introduction/introduction-to-the-lifecycle.html).
Локально окремо продемонструємо `test`, `package` та `verify`, пояснивши їхню різницю.

У межах цієї роботи CD — доступний після перевірок артефакт JAR,
як визначає методичка. Використання артефактів описано в
[документації GitHub](https://docs.github.com/en/actions/tutorials/store-and-share-data).

**Перевірка етапу:** збірка через Wrapper проходить; початкова програма
пакується й запускається з JAR; workflow проходить на трьох ОС та зберігає
артефакти. Перевірки CSV і показників у CI підключаємо після їх реалізації.

## 3. Дані й поведінка — рівень 1

Формат без заголовка чи коментарів, UTF-8:

```text
date;temperature;humidity;pressure;wind
```

У цьому описі рядок позначає порядок полів. У CSV замість назв записуються
тільки значення. Одиниці: °C, %, гПа, м/с.

Запропоновані правила, які зафіксуємо в README й тестах:

- Рівно п'ять полів; крайні пробіли прибираємо, порожнє останнє поле
  зберігаємо через `split(";", -1)` для перевірки.
- `date` — непорожній текст формату `YYYY-MM-DD`; календарний розбір
  не потрібен для цієї лабораторної.
- Чотири числові поля — скінченні `double`, десятковий роздільник — крапка.
  `NaN` та нескінченності вважаємо помилкою.
- Температура може бути від'ємною. Вологість — від 0 до 100 включно;
  тиск — більше 0; вітер — не менше 0. Ці діапазони й одиниці є
  нашими предметними домовленостями, оскільки таблиця їх не уточнює.
- Некоректний рядок не змінює статистику; повідомлення містить його
  фізичний номер у файлі й причину. Обробка наступних рядків триває.
- Якщо коректних записів немає, кількість дорівнює 0, а решта показників
  відображаються як «немає даних» без ділення на нуль.

Зразок для майбутнього `LAB_01/data/input.csv`:

```text
2026-09-01;-5.5;70.0;1013.0;3.2
2026-09-02;2.0;80.0;1008.0;7.5
2026-09-03;10.0;60.0;1010.0;1.8
2026-09-04;4.0;помилка;1012.0;2.0
2026-09-05;6.0;65.0;1011.0;-1.0
```

Очікування: **3** коректні записи, **−5.50 °C**, **70.00 %**,
**7.50 м/с**, **2** помилки. Українські символи є в хибному числовому полі;
додатково перевіримо український текст звіту й шляхи з українськими літерами.
До коректної дати не додаємо стороннього тексту заради Unicode-прикладу.

## 4. Предметний код — по одному завданню

1. Студент реалізує `--help` і розбір `--input` / `--output`;
   окремо обробляє невідомі параметри й відсутні значення.
2. Додає читання UTF-8 через `Path` і `Files`; стандартний вхід —
   `data/input.csv` від поточної робочої директорії, стандартний вихід —
   `out/report.txt`. Із кореня репозиторію вказуємо явний шлях до `LAB_01/data`.
3. Додає перевірку одного рядка, числові перетворення та список помилок.
4. Обчислює тільки за коректними записами кількість, мінімальну
   температуру, середню вологість і максимальний вітер.
   Тиск перевіряється, хоча не входить до показників 2–4.
5. Формує один текст звіту через `printf` / `String.format`,
   `Locale.ROOT`, два знаки після крапки й `%n`.
6. Виводить цей текст у консоль і файл UTF-8. Перевіряє також вихід
   `report.txt` без батьківського каталогу та помилки вводу/виводу.
7. Підключає `--version` до підготовленого Maven-ресурсу.
8. Додає javadoc до класів, `main` і нетривіальних методів.

Читання, перевірка, обчислення й форматування мають бути окремими
зрозумілими методами. На першій лабораторній не ускладнюємо модель власними
класами метеозаписів: це буде завдання лабораторної № 2.

**Перевірка:** числа з прикладу збігаються з очікуваннями, помилки
пояснено, вміст файлового звіту відповідає консольному.

## 5. Перевірка, документація та здача

JUnit-тести перевіряють фактичну поведінку програми:

- коректний рядок, пробіли, порожній рядок / поле й неправильну кількість полів;
- хибні числа, `NaN`, нескінченності, від'ємну температуру та від'ємний вітер;
- межі вологості 0 і 100, вихід за межі, нульовий / від'ємний тиск;
- змішані дані, порожній файл і файл без коректних записів;
- мінімальну температуру, максимум вітру та дробове середнє з похибкою;
- параметри CLI, `--help`, `--version`, відсутній файл;
- UTF-8, українські шляхи, файл звіту без батьківського каталогу;
- незалежність числового формату від локалі.

Кожен фактично знайдений дефект оформлюємо Issue й пов'язуємо з виправленням.
Рецензент перевіряє PR за вимогами, тестами та здатністю студента пояснити код.

README міститиме точний формат, правила перевірки, приклади, команди для
Windows/macOS/Ubuntu й посилання на CI. REPORT матиме всі 12 розділів
методички: тему й варіант; мету; задачу; структуру; інфраструктуру; Issues/PR;
приклади; тестування; документацію; академічну доброчесність; відповіді
на 20 контрольних питань; висновки. Відповіді й пояснення студент формулює
своїми словами з моєю допомогою.

У REPORT фіксуємо назву інструмента ШІ, ролі, запити, прийняті рекомендації,
реальний внесок студента та асистента. Додаємо фактичні посилання на Issues,
PR, успішні запуски трьох ОС і артефакти.

Після зеленого CI й рев'ю зливаємо PR у `main`, створюємо Git-тег `v1.0.0`
на завершеному коміті, запускаємо CI для тега й перевіряємо узгодженість
`pom.xml`, тега та `--version`. Розрізняємо версію коду `1.0.0` і номер
запуску workflow. Завершені документи додаємо до фінального PR до тегування.

Для ВНС готуємо звіт `.docx` або `.pdf` із посиланням на репозиторій.
На захисті показуємо програму, помилкові дані, тести, аналізатор, три ОС,
JAR, Issues, PR, версію й пояснення коду.

Додатковий запуск на embedded-пристрої / іншій архітектурі та рев'ю роботи
одногрупника можливі за наявності пристрою або доступу до чужого PR.
Їх не зараховуємо без фактичного виконання й доказів.
